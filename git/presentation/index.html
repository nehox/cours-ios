Fondations

Le modèle mental : 4 zones

Un fichier ne passe pas directement de votre éditeur à GitHub. Il traverse plusieurs zones. Comprendre ce trajet évite 90 % des confusions.

01

Dossier de travail

Vos fichiers modifiés, pas encore indexés.

02

Index / staging

Ce que vous préparez pour le prochain commit.

03

Dépôt local

Vos commits, stockés dans .git.

04

Dépôt distant

GitHub, GitLab… souvent appelé origin.

le trajet d'une modification 
Dossier de travail  -- git add -->  Index  -- git commit -->  Dépôt local  -- git push -->  origin
                          <-- git restore --          <-- git reset --          <-- git fetch / pull --
Un commit n'est pas un fichier. C'est un snapshot de votre projet + un message + un auteur + une date + un ou plusieurs parents. Git conserve l'historique, pas une copie de chaque fichier à chaque fois.

Le réflexe

Le cycle quotidien

La boucle que vous répétez toute la journée. git status est votre tableau de bord : lancez-le avant et après chaque action.

boucle de base 
# 1. Voir où j'en suis
git status

# 2. Préparer les changements
git add src/AuthView.swift

# 3. Enregistrer un snapshot
git commit -m "feat(auth): add login screen"

# 4. Publier
git push

Visualiser l'historique

La commande à garder sous la main :

git log --oneline --graph --decorate --all

Indexer par petits morceaux

git add -p permet de choisir les hunks à inclure. Parfait pour ne pas mélanger deux intentions dans un même commit.

À éviter

git add . sans regarder : vous risquez d'ajouter des fichiers temporaires, des secrets ou du bruit.

Qualité

Anatomie d'un bon commit

Un commit n'est pas une sauvegarde automatique. C'est un message pour la personne qui lira l'historique dans six mois — souvent vous.

🎯

Atomique

Une seule intention par commit. Pas de mélange refactor + feature.

✅

Qui compile

Chaque commit doit laisser le projet dans un état fonctionnel.

💬

Qui explique

Le message dit pourquoi, pas seulement quoi.

📏

Court et précis

Sujet ≤ 50 caractères, corps à 72 caractères par ligne.

✓ Bons réflexes

  • • Verbe à l'impératif : add, fix, remove.
  • • Pas de point final dans le sujet.
  • • Contexte dans le corps si nécessaire.
  • • Référencer l'issue : Refs: #42.

✗ À bannir

  • • update, fix, wip, modif.
  • • final final v2.
  • • Un commit fourre-tout de 40 fichiers.
  • • Un message qui ne dit pas pourquoi.

Conventional Commits

Le format qui parle tout seul

Une convention simple, adoptée par de nombreux projets open source. Elle rend l'historique lisible par les humains et exploitable par les outils.

structure type(scope)!: description 
<type>(<scope>)!: <description>

[corps optionnel]

[footer(s) optionnel(s)]

Exemples

feat(auth): add Google sign-in

fix(profile): correct avatar upload

docs(readme): explain setup

refactor(cart): extract total calculation

feat(api)!: remove v1 endpoints

Pourquoi c'est utile

  • ✓ Historique scannable en un coup d'œil.
  • ✓ Génération automatique de changelog.
  • ✓ Versionnement sémantique plus simple.
  • ✓ Filtrage : git log --grep="^fix".
  • ✓ Revue de code plus rapide.

Référence : conventionalcommits.org

Vocabulaire

Les types de commits

Choisissez le type qui décrit l'intention principale. En cas de doute, demandez-vous : « qu'est-ce que ce commit apporte au projet ? »

feat

Nouvelle fonctionnalité visible par l'utilisateur.

feat(search): add filters

fix

Correction d'un bug.

fix(cart): prevent double submit

docs

Documentation uniquement.

docs(setup): add Firebase steps

style

Formatage, espaces, virgules. Pas de logique.

style(ui): format AuthView

refactor

Réorganisation sans changer le comportement.

refactor(auth): extract validator

perf

Amélioration des performances.

perf(list): cache decoded images

test

Ajout ou correction de tests.

test(auth): cover invalid email

build

Outillage, dépendances, configuration de build.

build(spm): add Firebase package

ci

Pipeline d'intégration continue.

ci: run tests on pull request

chore

Tâches diverses qui ne rentrent pas ailleurs.

chore: update .gitignore

revert

Annulation d'un commit précédent.

revert: feat(auth): add login

À retenir : feat et fix sont les deux types qui influencent directement le versionnement sémantique. Les autres sont utiles pour la lisibilité et l'outillage.

Aller plus loin

Scope, corps, footer et breaking change

Le sujet suffit souvent. Quand le commit est plus complexe, ajoutez du contexte sans noyer le lecteur.

Scope

Le module concerné, entre parenthèses : auth, profile, api.

Corps

Explique le pourquoi, les compromis, le contexte. Ligne vide après le sujet.

Breaking change

Un ! après le type/scope, et un footer BREAKING CHANGE:.

exemple complet 
feat(auth)!: replace session cookies with JWT

The mobile client no longer stores cookies.
Sessions now use short-lived access tokens.

BREAKING CHANGE: /login no longer returns Set-Cookie.
Refs: #128

Le !

Signale immédiatement une rupture de compatibilité. Les outils peuvent alors incrémenter la version MAJOR.

Le footer

Références d'issues, co-auteurs, breaking change. Une ligne par information, après une ligne vide.

Démo

Générateur de message

Jouez avec les champs pour voir le format se construire. Ce n'est pas un TP : juste un aperçu concret.

message généré 
feat: <description>

Astuce : le sujet doit rester court. Si vous avez besoin de plusieurs phrases, utilisez le corps du commit.

Comparaison

Bons vs mauvais messages

Le même changement peut être raconté de deux façons. La bonne version permet de comprendre l'intention sans ouvrir le diff.

✗ Difficile à relire

update

fix bug

WIP

modif

final final v2

Impossible de savoir quoi, où, ni pourquoi. Le diff devient la seule source de vérité.

✓ Clair et actionnable

fix(cart): prevent double submit

feat(search): add debounce to query input

docs(setup): document Firebase configuration

refactor(auth): extract password validator

test(profile): cover empty display name

On sait immédiatement quel module est touché et quelle intention est servie.

Test simple : si vous devez ouvrir le diff pour comprendre votre propre message, c'est qu'il n'est pas assez précis.

Commande

git commit

Enregistre le contenu de l'index dans un nouveau commit. C'est une action locale : rien n'est encore publié.

les variantes utiles 
# Message sur une ligne
git commit -m "feat(auth): add login screen"

# Ouvre l'éditeur pour un message multi-ligne
git commit

# Ajoute les fichiers déjà suivis ET commit (pas les nouveaux fichiers)
git commit -am "fix(ui): correct spacing"

# Commit vide, utile pour déclencher une CI
git commit --allow-empty -m "ci: trigger pipeline"

Inspecter

git show HEAD
git log -1 --stat

HEAD pointe sur le commit courant.

Attention à -a

-a ne prend pas les fichiers non suivis. Faites git add pour les nouveaux fichiers, puis git commit.

Corriger

git commit --amend

Remplace le dernier commit par un nouveau. Pratique pour corriger un message ou ajouter un fichier oublié… tant que le commit n'est pas partagé.

corriger le dernier commit 
# Ajouter un fichier oublié, sans changer le message
git add src/AuthView.swift
git commit --amend --no-edit

# Corriger le message
git commit --amend -m "fix(auth): correct typo"

Ce qui se passe

Avant : A -- B -- C
Après : A -- B -- C'

Le commit C est remplacé par C' : le hash change.

Règle d'or

Uniquement sur un commit local non poussé. Si le commit est déjà sur le remote, prévenez l'équipe et utilisez git push --force-with-lease.

Publier

git push

Envoie vos commits locaux vers le dépôt distant. push ne fusionne rien : il publie votre historique.

publier proprement 
# Première fois : lie la branche locale à origin/main
git push -u origin main

# Ensuite, si l'upstream est configuré
git push

# Pousser une branche de fonctionnalité
git push origin feature/login

# Après un rebase ou un amend sur VOTRE branche
git push --force-with-lease

# Pousser les tags
git push --tags

-u / --set-upstream

Retient la branche distante. Les prochains git push et git pull sauront où aller.

--force-with-lease

Force le push seulement si personne n'a poussé entre-temps. Plus sûr que --force.

Jamais sur main

Ne forcez pas un push sur une branche partagée. Vous écraseriez le travail des autres.

Synchroniser

git pull et git fetch

fetch télécharge les nouveautés sans toucher à votre travail. pull télécharge puis intègre dans votre branche courante.

les commandes 
# Met à jour origin/main sans modifier vos fichiers
git fetch

# fetch + merge dans la branche courante
git pull

# fetch + rejoue vos commits locaux par-dessus
git pull --rebase

# Refuse si ce n'est pas un fast-forward
git pull --ff-only

En cas de conflit

  1. Ouvrez les fichiers en conflit.
  2. Gardez / fusionnez les bonnes lignes.
  3. git add les fichiers résolus.
  4. git commit (merge) ou git rebase --continue.

Bonne habitude

Faites un git pull --rebase avant de commencer à travailler. Vous éviterez les merge commits inutiles.

Copier un commit

git cherry-pick

Prend les changements d'un commit existant et les rejoue sur la branche courante, sous la forme d'un nouveau commit.

exemple 
# Se placer sur la branche cible
git switch release

# Rejouer un commit précis
git cherry-pick 3f2a9c1

# En cas de conflit
git add .
git cherry-pick --continue

# Tout annuler
git cherry-pick --abort

Quand l'utiliser

  • • Récupérer un hotfix de main vers release.
  • • Récupérer un commit isolé d'une autre branche.
  • • Sauver un commit avant de supprimer une branche.

À savoir

Le nouveau commit a un hash différent. L'original reste où il est. Ne cherry-pickez pas une branche entière : utilisez merge ou rebase.

git switch est la commande moderne pour changer de branche ; git checkout reste valable mais fait aussi d'autres choses.

Réécrire

git rebase

Rejoue les commits de votre branche par-dessus une autre base. Résultat : un historique linéaire, plus facile à lire.

rebaser sa branche sur main 
git switch feature/login
git rebase main

# En cas de conflit
git add fichier.swift
git rebase --continue

# Annuler le rebase
git rebase --abort

Avant / après

Avant :
main    A -- B
              \
feature        C -- D

Après rebase :
main    A -- B -- C' -- D'
                      feature

Les commits C et D sont réécrits en C' et D'. Les hashes changent.

Règle absolue : ne rebasez jamais une branche que d'autres personnes ont déjà récupérée. Vous réécririez leur historique.

Nettoyer

git rebase -i

Le rebase interactif ouvre la liste de vos commits dans un éditeur. Vous choisissez quoi garder, renommer, fusionner ou supprimer.

git rebase -i HEAD~4 les 4 derniers commits 
pick   1a2b3c4 feat(auth): add login form
squash 5d6e7f8 fix typo
reword 9a0b1c2 docs: update setup
drop   3c4d5e6 debug print

pick

Garder le commit tel quel.

reword

Garder le commit, changer le message.

edit

S'arrêter pour modifier le contenu.

squash

Fusionner avec le précédent, garder le message.

fixup

Fusionner en jetant le message.

drop

Supprimer le commit.

Cas d'usage : avant d'ouvrir une pull request, fusionnez les commits « wip », « fix typo » et « debug » pour ne garder que des commits propres et lisibles.

Sécurité

Les règles d'or du rebase

Le rebase est puissant, mais il réécrit l'histoire. Ces règles vous évitent de casser le travail de l'équipe.

✓ Branche personnelle

Rebasez librement une branche de fonctionnalité que vous seul utilisez.

✗ Branche partagée

Jamais sur main, develop ou une branche que d'autres ont pull.

↺ Après rebase

Poussez avec --force-with-lease, jamais --force seul.

⎇ Sauvegarde

En cas de doute : git branch backup-avant-rebase.

⇄ Merge vs rebase

Merge préserve l'histoire. Rebase la linéarise. Choisissez selon la convention de l'équipe.

🧠 En cas de doute

Ne rebasez pas. Un merge est toujours plus sûr qu'un historique cassé.

filet de sécurité 
git branch backup-avant-rebase
git rebase main
# Si tout va bien, supprimez la sauvegarde
git branch -D backup-avant-rebase

Versionner

git tag

Un tag est une étiquette fixe sur un commit. Contrairement à une branche, il ne bouge pas. Parfait pour marquer une release.

créer et publier 
# Lister les tags
git tag

# Tag léger (simple pointeur)
git tag v1.2.0

# Tag annoté (recommandé pour une release)
git tag -a v1.2.0 -m "Release 1.2.0"

# Inspecter
git show v1.2.0

# Pousser un tag (les tags ne partent pas avec git push)
git push origin v1.2.0
git push --tags

Semver : MAJOR.MINOR.PATCH

MAJOR : rupture de compatibilité.

MINOR : nouvelle fonctionnalité compatible.

PATCH : correction compatible.

Supprimer un tag

git tag -d v1.2.0
git push origin --delete v1.2.0

Tag ≠ branche

Un tag ne reçoit pas de nouveaux commits. Pour continuer à développer, créez une branche à partir du tag.

Travailler en parallèle

git worktree

Un seul dépôt, plusieurs dossiers de travail. Chaque worktree a sa propre branche, sans clone ni stash.

commandes 
# Ajouter un worktree sur une branche existante
git worktree add ../hotfix hotfix

# Créer une branche + un worktree
git worktree add -b feature/search ../search main

# Lister les worktrees
git worktree list

# Supprimer un worktree
git worktree remove ../hotfix

# Nettoyer les références obsolètes
git worktree prune

Un dépôt, deux dossiers

mon-projet/          ← worktree principal (main)
├── .git/            ← un seul dépôt
└── src/

../hotfix/           ← worktree secondaire (hotfix)
└── src/

Quand l'utiliser

  • • Corriger un bug urgent sans perdre votre travail en cours.
  • • Comparer deux branches côte à côte.
  • • Lancer des tests en parallèle sur deux versions.

Limite

Une même branche ne peut pas être checkout dans deux worktrees en même temps.

Pièges

Les erreurs fréquentes

La plupart des problèmes Git viennent de trois causes : aller trop vite, réécrire une branche partagée, ou ne pas regarder ce qu'on ajoute.

🔑 Committer un secret

Clé API, .env, certificat… Si c'est poussé, considérez-le comme compromis et changez-le.

📦 git add . aveugle

Vérifiez git status et git diff avant de committer.

💥 Force push partagé

Vous écrasez les commits des autres. Sur une branche partagée, ne forcez jamais.

🧹 Rebase après pull

Si quelqu'un a déjà récupéré la branche, le rebase casse son historique.

✏️ Amend après push

Le commit distant ne correspond plus. Coordonnez-vous avant de réécrire.

🗑️ Commit fourre-tout

Refactor + feature + formatting dans un seul commit : impossible à relire ou à revert.

Réflexe : avant chaque commit, demandez-vous « est-ce que je pourrais annuler ce commit seul sans casser autre chose ? ». Si la réponse est non, découpez-le.
